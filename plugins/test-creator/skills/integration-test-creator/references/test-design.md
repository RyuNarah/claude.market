# 통합 시나리오 설계 — 의미 있는 연동 도출법

목표는 **여러 컴포넌트가 실제로 엮여 만들어내는 동작의 검증**이다. 순수 로직 분기(모든 return·조건·극치 입력)는 단위 테스트의 몫이므로 여기서 반복하지 않는다. 통합 테스트는 단위가 닿지 못하는 곳 — **경계 계약, 실데이터 왕복, 실제 실패, 자원 수명** — 을 사냥한다. 컴포넌트/흐름마다 아래를 도출한다. 실제 자원은 임시로 격리하고 정리한다(→ `references/conventions.md` §7).

## 1. 해피패스 end-to-end 흐름
대표 입력으로 전체 흐름이 기대 산출물을 내는지. 흐름의 시작과 끝만 단언하지 말고, 중간 산출물도 의미가 있으면 확인한다.
예) 샘플 파일 → 디코더 → 프레임 추출 → 기대 프레임 수/해상도/타임스탬프.

## 2. 컴포넌트 경계 계약
한 컴포넌트의 출력이 다음 컴포넌트의 입력 가정과 **실제로 일치**하는지. 단위 테스트에서 각자 Mock으로 "이런 형태로 주고받을 것"이라 가정했던 계약이 맞는지 검증한다 — **통합 테스트가 가장 큰 값을 내는 지점**이다.
예) 파서가 만든 메타데이터를 변환기가 그대로 소비할 수 있는가, enum/단위/좌표계가 일치하는가.

## 3. 실데이터 왕복 (round-trip)
저장→로드, 인코딩→디코딩, 직렬화→역직렬화가 원본과 동등한 결과를 내는지. 실제 자원의 타입 변환·매핑 정확성을 잡는다.
예) 실제 SQLite에 엔티티를 저장한 뒤 다시 읽어 동일성 확인(`BeEquivalentTo`) — OrmLite/IBatis 매핑, 날짜·바이너리·널 처리.

## 4. 설정 / 환경 변형
실제로 달라질 수 있는 조건에서 동작하는지.
- 스키마 버전·`MetaInfo` 버전, **마이그레이션 경로**(구버전 DB → 현재 버전).
- 코덱·컨테이너·포맷 조합, 플랫폼(x64) 차이.
- 설정 파일/매핑(SqlMap 등) 변형.

## 5. 실제 의존성 실패 모드
실제 자원이 실패하는 상황을 **실제로 일으켜** 검증한다(Mock으로 흉내내지 않는다).
- 파일: 없음, 손상, 부분(잘린) 입력, 잠김/권한 오류.
- DB: 잠김, 제약 위반(UNIQUE/FK), 스키마 불일치, 트랜잭션 롤백.
이때 적절한 **예외 타입**·복구·정리(핸들 해제, 트랜잭션 롤백)가 일어나는지 단언한다.

## 6. 자원 수명 · 정리
- 파일 핸들·DB 연결·임시 파일이 누수 없이 해제되는지(실패 경로 포함).
- 같은 흐름을 **반복 실행**해도 자원·잠금·임시물이 쌓이지 않는지.
- 검증 방법: 작업 후 같은 파일을 다시 열거나 삭제 가능한지, 임시 디렉터리가 비는지.

## 7. 순서 · 멱등 · 동시성
- 여러 단계의 실행 **순서 의존성**(준비 없이 호출하면?).
- 같은 작업의 **재실행 멱등성**(두 번 저장/복구해도 결과가 안정적인가).
- 실제 공유 자원(DB·파일)에 대한 **동시 접근** 시 동작(필요하면 `[Collection]`으로 직렬화하거나, 동시성 자체를 검증).

> 통합 시나리오는 "모든 조합"이 아니라 **실제로 의미 있는 상호작용과 실패**에 집중한다. 조합 폭발을 피하고, 단위에서 이미 망라한 분기는 반복하지 않는다. 시나리오를 만들다 연동 결함(경계 불일치, 흐름 중간 데이터 변형, 정리 누락)을 발견하면 테스트로 박제하고 보고한다.

## 시나리오를 코드로 옮기기

### 왕복(round-trip) — 실제 자원 격리·정리

```csharp
/// <summary>
/// 증거물을 실제 SQLite에 저장한 뒤 다시 읽으면 동일하다 — OrmLite 매핑·타입 변환의 실제 정확성을 박제한다.
/// 매핑이 깨지면 사건 DB에서 증거물 메타데이터가 유실/왜곡된다.
/// </summary>
[Fact]
[Trait("Category", "Integration")]
public void SaveThenLoad_RoundTripsEvidence()
{
    var evidence = new Evidence { Id = 1, Name = "clip.mp4", CapturedAt = new DateTime(2026, 1, 2, 3, 4, 5) };

    _sut.Save(evidence);
    var loaded = _sut.Load(1);

    loaded.Should().BeEquivalentTo(evidence);   // 모든 필드 동일성
}
```

### 실데이터 흐름 — `[Theory]`로 여러 샘플

```csharp
/// <summary>실제 샘플 파일을 디코딩하면 컨테이너가 보고한 프레임 수와 일치한다(디코더+컨테이너 연동).</summary>
[Theory]
[Trait("Category", "Integration")]
[InlineData("sample_h264.mp4", 300)]   // 표준 H.264
[InlineData("sample_short.mp4", 12)]   // 매우 짧은 클립 — 경계
public void Decode_RealSampleFile_ProducesExpectedFrameCount(string fileName, int expected)
{
    var path = Path.Combine(_fixture.SampleDir, fileName);

    var frames = _sut.DecodeAll(path);

    frames.Should().HaveCount(expected);
}
```

### 실패 모드 — 실제로 일으키고 정리 검증

```csharp
/// <summary>손상된 파일을 열면 InvalidDataException을 던지고 파일 핸들을 해제한다(부분 입력 방어 + 자원 정리).</summary>
[Fact]
[Trait("Category", "Integration")]
public void Open_CorruptFile_ThrowsAndReleasesHandle()
{
    var corrupt = Path.Combine(_fixture.SampleDir, "sample_corrupt.mp4");

    var act = () => _sut.Open(corrupt);

    act.Should().Throw<InvalidDataException>();
    var reopen = () => File.OpenWrite(corrupt);   // 핸들이 풀렸으면 가능해야 함
    reopen.Should().NotThrow();
}
```

### 기존 테스트에 시나리오를 더할 때 — 붙이지 말고 정리한다

대상에 통합 테스트가 이미 있으면, 새 시나리오를 파일 끝에 그냥 덧붙이지 말고 **기존 테스트를 먼저 읽고 전체를 하나의 응집된 스위트로 다듬는다.** 판단 기준은 **"검증하는 연동이 같은가"** 다.

- **통합**: 새 시나리오가 기존 테스트와 같은 연동을 다른 샘플·설정으로 검증하면(예: 다른 코덱, 다른 스키마 버전, 다른 크기의 파일), 그 테스트를 `[Theory]`(`[InlineData]`/`[MemberData]`)로 바꿔 한곳에 모은다.
- **분리**: 한 테스트가 서로 다른 흐름·경계 계약·실패 모드를 뭉뚱그려 단언하고 있으면 시나리오별로 쪼갠다. 실패했을 때 이름만 보고 어떤 연동이 깨졌는지 알 수 있어야 한다.
- 통합·분리로 손댄 기존 테스트도 반드시 다시 통과시키고, 자원 격리·정리가 여전히 유효한지 확인한다.

### 연동 결함을 발견하면

시나리오를 만들다 연동 결함(경계 계약 불일치, 흐름 중간 데이터 변형, 정리 누락, 마이그레이션 실패)을 찾으면:

1. 그 동작을 드러내는 테스트를 작성한다.
2. **현재의 잘못된 동작에 맞춰 통과시키지 않는다.** 올바른 기대값으로 작성해 실패하게 두고,
3. "이런 흐름/입력에서 이런 연동 결함이 보인다, 기대 동작은 이렇다"고 사용자에게 보고해 수정으로 이어지게 한다.

## 동작 검증 vs 구현 검증

| 검증할 것(O) | 피할 것(X) |
|---|---|
| 실제 산출물(추출 프레임·저장된 행·생성 파일) | 내부 메서드 호출 순서 자체 |
| 왕복 후 데이터 동일성 | private 상태 직접 확인 |
| 던진 예외(타입)와 그 후 자원 상태(정리) | 구현 세부에 묶인 호출 횟수 |
| 흐름 종료 후 부수효과(파일/DB 변화) | 리팩터링하면 깨지는 구조 의존 |

통합 테스트는 **흐름의 결과와 부수효과**를 본다. "내부적으로 A→B 순서로 불렀다" 같은 구현 검증이 아니라, "이 입력으로 흐름을 돌리면 DB에 이런 행이 남고, 이 파일이 생성된다"를 단언한다.

**예외는 타입만 단언한다.** 실패 모드에서 어떤 예외가 나는지는 계약이지만, 고정된 문자열 메시지는 구현 세부이고 쉽게 바뀐다 — 메시지에 의존하면 문구만 손봐도 테스트가 깨진다. `act.Should().Throw<InvalidDataException>()`까지가 검증이고, `.WithMessage("...")`로 고정 메시지를 확인하는 것은 하지 않는다(메시지가 그 자체로 계약인 특수한 경우가 아니라면). 예외 뒤의 **자원 상태(정리)** 는 별개의 관찰 가능한 결과이므로 계속 단언한다.
