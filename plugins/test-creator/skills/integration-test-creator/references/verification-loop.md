# 독립 검증 — 검증 에이전트 협상 루프

작성한 통합 테스트가 **의미 있는 연동 시나리오를 빠짐없이 검증했는지**를, 테스트를 만든 사람(메인 에이전트)이 스스로 채점하지 않고 **컨텍스트를 공유하지 않는 검증 에이전트**에게 독립적으로 확인받는 절차다. 검증자가 통과시킬 때까지 반복하되, 검증자의 판단도 틀릴 수 있으므로 메인과 근거를 주고받으며 타협점을 찾는다.

## 왜 이렇게 하는가

메인 에이전트가 "이 흐름은 이런 경계 계약이 있고 이렇게 시나리오를 짰다"는 **자기 분석과 근거를 그대로 검증자에게 넘기면**, 검증자는 같은 사고의 맹점을 그대로 물려받아 검증이 형식적이 된다. 그래서 검증자에게는 **관련 소스(컴포넌트들)와 테스트 코드의 경로만** 주고, 메인이 어떻게 시나리오를 도출했는지는 알려주지 않는다. 검증자는 소스만 보고 **연동 지점과 필요한 시나리오를 처음부터 스스로 다시 열거**한 다음 실제 테스트와 대조한다. 이 독립성이 이 절차의 전부다 — 공유하는 순간 가치가 사라진다.

## 루프 개요

```
메인(생성자)                          검증자(컨텍스트 미공유 서브에이전트)
  │  ① 소스(컴포넌트들)+테스트 경로만 전달 │
  │     (자기 분석·근거는 숨김)          │
  │ ───────────────────────────────────▶ │ ② 소스만 보고 연동 지점·필요 시나리오 독립 재도출
  │                                       │    → 실제 테스트와 대조
  │ ◀─────────────────────────────────── │ ③ 구조화된 판정 반환 (PASS/FAIL + gaps)
  │  ④ 판정을 심사: 항목별로               │
  │     수용(시나리오 추가) / 반박(근거) / │
  │     에스컬레이션                       │
  │ ───────────────────────────────────▶ │ ⑤ 같은 인스턴스가 재검토 (SendMessage)
  └──────────── PASS 나올 때까지 반복 ─────┘   (종료 조건 도달 시 중단)
```

## ① 검증자 스폰 — 무엇을 주고 무엇을 숨기나

- **일반(fresh) 서브에이전트**로 띄운다. `Agent` 툴에서 `subagent_type`을 `general-purpose`로 하되 **`fork`는 절대 쓰지 않는다** — fork는 메인 컨텍스트를 상속하므로 독립성이 깨진다.
- 전달하는 것: **연동에 참여하는 소스 파일/컴포넌트 경로**, **작성한 통합 테스트 파일 경로**, 검증 지침(아래 프롬프트). 그게 전부다.
- 숨기는 것: 메인이 도출한 시나리오 목록, 경계 계약 분석, "이건 이래서 뺐다" 같은 판단 근거. 검증자가 백지에서 재도출하도록 둔다.
- 협상을 이어가려면 **같은 검증자 인스턴스에 `SendMessage`로 대화를 잇는다.** 라운드마다 새 에이전트를 띄우면 협상 이력이 사라져 이미 합의한 지적이 계속 되살아난다.

## ② 검증자에게 줄 프롬프트(템플릿)

```
너는 통합 테스트의 시나리오 커버리지를 독립적으로 검증하는 에이전트다. 테스트를 작성한
사람의 판단을 신뢰하지 말고, 소스만 보고 필요한 연동 시나리오를 처음부터 다시 도출해 대조하라.

연동 대상 소스: <컴포넌트 소스 파일 경로들>
작성된 통합 테스트: <테스트 파일 경로>

순서를 지켜라(중요):
1. 먼저 테스트를 보지 말고 **소스만** 읽어라. 그리고 이 연동이 반드시 검증해야 할
   시나리오를 스스로 남김없이 열거하라:
   - 해피패스 end-to-end 흐름(대표 입력 → 기대 산출물)
   - 컴포넌트 경계 계약(한 컴포넌트의 출력이 다음의 입력 가정과 실제로 일치하는가)
   - 실데이터 왕복(round-trip): 저장→로드, 인코딩→디코딩, 직렬화→역직렬화의 원본 동등성
   - 설정/환경 변형: 스키마 버전·코덱·플랫폼 조합, 마이그레이션(구버전→현재) 경로
   - 실제 의존성 실패 모드: 파일 없음/손상/부분 입력, DB 잠김·제약 위반, 권한 오류 시 예외·복구·정리
   - 자원 수명·정리: 핸들·연결·임시 파일 누수 없이 해제, 반복 실행에도 자원 미축적
   - 순서·멱등·동시성: 단계 순서 의존성, 재실행 멱등성, 공유 자원 동시 접근
2. 그다음 실제 테스트를 읽고, 위에서 열거한 시나리오 중 **빠진 것/약한 단언/실제 자원을
   Mock으로 대체해 연동 검증이 무의미해진 것/정리 검증 누락**을 찾아라. 특히 다음을 반드시 확인하라:
   - **이름 규칙 준수**: 저장소/스킬에 명명 규칙이 있으면(예: `Scenario_ExpectedResult`, `[Trait("Category", "Integration")]` 부착) 이를 어긴 테스트가 있는지.
   - **실패 경로 검증**: 흐름이 성공과 실패(파일 없음/손상, DB 제약 위반, 부분 입력 등)를 모두 낼 수 있으면, 해피패스만이 아니라 **실패하는 경우도** 테스트했는지.
   - **구현이 아닌 결과 검증**: 관찰 가능한 결과·부수효과가 아니라 구현에 묶인 단언이 있는지. 특히 **고정된 메시지를 가진 예외를 테스트할 때 예외 메시지를 단언**하는 것은 구현 검증이다 — 예외 **타입**만 확인해야 한다(`.WithMessage(...)` 불필요). 내부 호출 순서에 묶인 단언도 여기 해당한다.
3. 불확실하면 통과가 아니라 FAIL 쪽으로 판단하라. 너의 임무는 봐주는 게 아니라 구멍을 찾는 것이다.

아래 형식으로만 응답하라:

verdict: PASS | FAIL
gaps:
  - id: G1
    kind: missing-happy-path | missing-boundary-contract | missing-roundtrip | missing-config-variant | missing-failure-mode | missing-cleanup | weak-assertion | over-mocked | implementation-coupled | naming-violation
    location: <컴포넌트/흐름>:<파일·라인>
    claim: <무엇이 빠졌거나 잘못됐는지 한 문장>
    severity: blocker | major | minor
    evidence: <소스의 근거와 테스트에 그 시나리오가 없다(또는 실제 자원이 Mock됐다)는 근거>
```

각 gap에 **id와 코드 근거(location/evidence)** 를 반드시 붙이게 한다. id가 있어야 이후 항목별로 "G1 수용, G3 반박"이 가능하다.

## ④ 메인의 심사 — 검증자 의견은 무조건 옳지 않다

판정을 받으면 gap을 **하나씩** 심사한다. 검증자가 옳다고 가정하지 말고 실제 코드로 확인한다.

| 판단 | 행동 |
|---|---|
| 정당한 지적 | 시나리오를 추가/수정하고 "G1 반영함"이라 알린다 |
| 잘못된 지적 | **코드 근거와 함께** 반박한다. 예: "G2의 실패 모드는 이 경계 밖 — 해당 자원은 상위 계층에서 검증되며 이 통합 범위의 계약이 아님. 기존 시나리오 X가 왕복을 이미 커버함" |
| 애매함 | 근거를 더 요청하거나 대안 시나리오를 제시한다 |

특히 통합 테스트에서는 **`over-mocked`(검증해야 할 실제 자원을 Mock으로 대체)** 지적을 진지하게 다룬다 — 실제 협력자를 연결하지 않으면 통합 테스트의 의미가 사라지기 때문이다.

## ⑤ 협상 규칙 — 무한 핑퐁과 서로 봐주기 방지

- 양쪽 다 **주장이 아니라 코드 근거로만** 의견을 바꾼다(경계 계약 명세, 범위 밖임을 보이는 근거, 기존 시나리오의 커버 입증).
- gap은 다음 중 하나로만 **해소**된다: (a) 메인이 시나리오를 추가함, (b) 검증자가 메인의 근거를 수용함, (c) 사용자에게 에스컬레이션.
- 검증자는 "불확실하면 FAIL", 메인은 "근거 없는 지적은 반박" — 서로 반대로 편향시켜 견제한다. 성급히 합의하지 않는다.

## 루프 종료 조건 (셋 중 하나)

1. **성공**: 검증자가 `PASS`를 반환한다.
2. **횟수 상한**: 최대 3~5 라운드. 초과하면 중단하고 **미해결 gap을 사용자에게 보고**한다.
3. **무진전 감지**: 한 라운드에서 (새로 추가한 시나리오 0개) AND (검증자가 수용한 gap 0개)이면 교착이다. 중단하고 쟁점을 사용자에게 넘긴다.

라운드마다 상태를 추적한다: `해소된 gap`, `미해결 gap`, `라운드 번호`, `직전 대비 진전 여부`.

## 선택: fresh-eyes 최종 게이트

루프 내내 같은 검증자로 진행하면 효율적이지만 자기 이전 판단에 앵커링될 수 있다. 마지막 `PASS` 직전에 **새 검증자 1회**를 붙여 완전히 독립적인 최종 확인을 받으면 협상 효율과 최종 독립성을 모두 얻는다. 필수는 아니며, 연동 범위가 넓거나 경계 계약이 복잡할 때 권장한다.

## 검증 대상은 5단계 이후

이 루프는 테스트가 **컴파일·통과되고 정리(임시 자원 삭제)까지 확인된 뒤**(SKILL.md 5단계) 돌린다. 컴파일도 안 되거나 자원이 새는 테스트를 검증자에게 넘기는 것은 시기상조다. 루프가 끝나야 비로소 보고서(6단계 이후)로 넘어간다.
