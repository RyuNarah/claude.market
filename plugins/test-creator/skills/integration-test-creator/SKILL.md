# Integration Test Creator

C#/.NET 코드에 대해 **여러 컴포넌트가 실제로 함께 동작하는지** 검증하는 xUnit 통합 테스트를 만든다. 단위 테스트가 각 부품을 Mock으로 격리해 검증한다면, 통합 테스트는 **실제 협력자**(실제 SQLite, 실제 샘플 파일, 실제 디코더·파이프라인)를 연결해 "부품들이 약속대로 맞물리는가"를 검증한다. 단위 테스트가 통과해도 경계 계약이 어긋나면 깨지는 결함 — SQL 매핑 오류, 포맷 디코딩 불일치, 흐름 중간의 데이터 변형 — 이 통합 테스트의 사냥감이다.

핵심 원칙: **실제 자원으로 검증하되, 임시 자원으로 격리하고 반드시 정리한다.** 테스트 간 상태가 새면 통합 테스트는 신뢰할 수 없다.

이 스킬의 가치는 **의미 있는 연동 시나리오 설계**와 **격리·정리가 보장된, 저장소 관례에 맞는 산출물**에 있다. 아래 절차를 순서대로 따른다.

## 0. 입력 확인 — 대상이 무엇인가

통합 테스트 대상은 **여러 컴포넌트가 엮이는 단위**다: 모듈 / 서브시스템 / 컴포넌트 쌍(예: 리포지토리+DB) / end-to-end 흐름(예: 파일→디코더→프레임) / 프로젝트.

- 대상이 명시되지 않았으면 **임의로 추측하지 말고** 사용자에게 무엇을 어디까지(어떤 컴포넌트 경계까지) 통합해 검증할지 되묻는다.
- 대상이 단일 클래스의 순수 로직 분기 검증이면, 그건 단위 테스트 영역이다 — `unit-test-creator`가 더 적합함을 알리고 범위를 합의한다.
- 통합 범위를 정한다: **어떤 컴포넌트를 실제로 함께 돌리고, 어디를 경계(외부 자원)로 둘지**. 범위가 너무 넓으면 흐름 단위로 쪼갠다.

**접근 제한자 규칙(중요):** 접근 제한자가 `internal` **이상**(internal/public)인 진입점을 통해 검증한다. `private`/`protected`를 테스트하려고 접근 제한자를 올리지 않는다. `internal` 진입점에 접근하려면 접근 제한자 변경이 아니라 `InternalsVisibleTo`로 접근한다(→ `references/conventions.md`).

## 1. 대상 분석 — 컴포넌트가 어떻게 엮이는가

통합 테스트의 질은 "무엇과 무엇이, 어떤 계약으로 맞물리는지"를 얼마나 정확히 파악했는가에 달렸다. 다음을 파악한다.

- **컴포넌트 구성과 연결**: 어떤 타입들이 협력해 하나의 동작을 이루는가. 데이터가 거치는 흐름(입력 → 단계들 → 산출물)과 각 단계의 변환.
- **경계 계약**: 한 컴포넌트의 출력이 다음 컴포넌트의 입력 가정과 맞아야 하는 지점. 단위 테스트에서 각자 Mock으로 가정했던 계약이 실제로 일치하는지가 핵심 검증 대상이다.
- **실제 필요한 자원**: DB(스키마·버전), 샘플 파일(포맷·크기), 설정, 환경. 무엇을 실제로 준비해야 하는가.
- **외부·비결정 경계**: 외부 네트워크·실시간 시계·난수처럼 통합 대상이 **아니면서** 재현성을 깨는 것. 이건 통합에서도 고정/추상화한다.
- **실패 모드**: 실제 자원이 실패할 수 있는 방식(파일 없음/손상, DB 잠김/제약 위반, 부분 입력)과 시스템이 어떻게 대응해야 하는가.
- **현재 사용처**: 실제 운영에서 이 흐름에 들어오는 입력·설정.

분석 범위가 넓으면(여러 파일·모듈을 훑어야 하면) `Explore`/`general-purpose` 에이전트로 컴포넌트 구성·의존성·사용처를 조사하고, 결론만 가져와 정리한다.

## 2. 테스트 가능성 판단 — 실제 연결을 위한 리팩터링

통합 대상이 **실제 협력자를 연결하고, 자원을 임시로 격리**할 수 있는 구조인지 본다. 막혀 있으면 **테스트 작성 전에 리팩터링을 제안**한다. 제안 시 항상 **(a) 왜 막히는지 (b) 어떤 방향으로 (c) 동작 보존**을 설명하고 사용자 동의를 받는다.

통합 테스트의 리팩터링 목표는 단위와 다르다. **DI seam을 확보하되, 그 자리에 실제 구현을 주입**한다(통합이 목적이므로 협력자를 Mock하지 않는다). 다음만 주의한다.

- **자원 경로가 하드코딩**되어 임시 위치로 바꿔 끼울 수 없음 → DB 경로·작업 디렉터리 등을 주입 가능하게(생성자/팩토리 인자). 그래야 임시 DB/temp 디렉터리로 격리한다.
- **`ServiceLocator`/정적 컨테이너로 협력자를 끌어옴** → 생성자 주입으로 전환(실제 구현 주입). (→ `references/refactoring.md`)
- **UI 의존성**(`MessageBox`, 다이얼로그, `Dispatcher` 등)이 흐름에 끼어 있음 → 인터페이스로 추상화. **단, Mock을 위해 메서드를 `virtual`로 바꾸는 방식은 쓰지 않는다.** (→ `references/refactoring.md`)
- **외부·비결정 경계**(외부 네트워크·실시간 시계·난수)가 결과를 좌우 → 인터페이스로 추상화해 통합 테스트에서 고정. **파일시스템·DB는 검증 대상 그 자체이므로 가짜로 대체하지 않고 실제로 쓰되 임시 자원으로 격리한다.**
- **자원 해제 경로가 없음**(Dispose/Close 불가) → 정리 가능하도록 보완.

리팩터링은 **동작을 바꾸지 않는 범위**에서 최소로 한다. 자세한 패턴·예시는 **`references/refactoring.md`** 를 읽고 적용한다.

## 3. 통합 시나리오 설계 — 의미 있는 연동에 집중

분석을 토대로 아래를 **시나리오로** 만든다. 순수 로직 분기는 단위 테스트의 몫이므로 여기서 반복하지 않는다. 각 항목의 도출법·예시는 **`references/test-design.md`** 에 정리돼 있다.

- **해피패스 end-to-end 흐름**: 대표 입력으로 전체 흐름이 기대 산출물을 내는지.
- **컴포넌트 경계 계약**: 한 컴포넌트의 출력이 다음의 입력 계약과 실제로 일치하는지(통합 테스트가 가장 큰 값을 내는 지점).
- **실데이터 왕복(round-trip)**: 저장→로드, 인코딩→디코딩, 직렬화→역직렬화가 원본과 동등한지.
- **설정/환경 변형**: 스키마 버전·코덱·플랫폼 조합, 마이그레이션(구버전 DB→현재) 경로.
- **실제 의존성 실패 모드**: 파일 없음/손상/부분 입력, DB 잠김·제약 위반, 권한 오류 시 적절한 예외·복구·정리.
- **자원 수명·정리**: 핸들·연결·임시 파일이 누수 없이 해제되는지, 반복 실행에도 자원이 쌓이지 않는지.
- **순서·멱등·동시성**: 단계 실행 순서 의존성, 재실행 멱등성, 실제 공유 자원에 대한 동시 접근.

> 동작을 검증하라 — 구현 방식이 아니라. 내부 호출 순서가 아니라 **관찰 가능한 결과**(실제 산출물·저장된 데이터·던진 예외·정리된 자원 상태)를 단언한다. 시나리오를 만들다 연동 결함(경계 계약 불일치, 흐름 중간 데이터 변형, 정리 누락)을 발견하면, 테스트로 박제하고 사용자에게 보고한다.

## 4. 테스트 작성 — 저장소 관례에 맞게

**작성 전에 반드시 `references/conventions.md` 를 읽는다.** 프로젝트 위치·명명·csproj 구성·라이브러리 버전·`InternalsVisibleTo`·폴더 구조·Fixture 패턴이 모두 거기 정의돼 있다. 핵심만 요약:

- **프레임워크/라이브러리**: xUnit, 단언은 **AwesomeAssertions**(네임스페이스는 `using FluentAssertions;`). 통합 테스트는 실제 협력자를 쓰므로 **NSubstitute는 최소화**(진짜 외부 경계에만). 실제 자원 라이브러리(예: `Microsoft.Data.Sqlite`)는 검증에 필요할 때 참조한다.
- **위치/구조**: `Tests/` 루트 아래 원본 폴더 구조를 미러링. 프로젝트명 `<대상프로젝트>.IntegrationTests`(실제 자원·느린 테스트는 단위 프로젝트와 분리). 클래스는 시나리오/대상 중심 이름(예: `CaseDbIntegrationTests`, `VideoAnalysisPipelineTests`).
- **메서드명**: `Scenario_ExpectedResult`(흐름 중심). 예: `SaveThenLoad_RoundTripsEvidence`, `Decode_RealSampleFile_ProducesExpectedFrames`, `Open_CorruptFile_ThrowsAndCleansUp`.
- **격리·정리**: 비싼 실제 자원은 `IClassFixture`/`ICollectionFixture`로 공유, `IDisposable`/`IAsyncLifetime`로 setup/teardown. 임시 DB·temp 디렉터리를 쓰고 끝나면 삭제. 경합 가능하면 `[Collection]`으로 직렬화.
- **분류**: 모든 통합 테스트에 `[Trait("Category", "Integration")]`을 붙여 빠른 단위 실행과 분리한다.
- **샘플 파일**: 실제 데이터가 핵심이면 `TestData/`에 최소 샘플을 두고 `CopyToOutputDirectory="PreserveNewest"`로 출력에 복사한다.
- **`internal` 진입점**: 소스 csproj에 `<InternalsVisibleTo Include="...IntegrationTests" />` 추가(접근 제한자 변경 금지).
- **기존 테스트가 있으면 그 위에 정리한다**: 대상에 통합 테스트가 이미 있으면 새 시나리오를 파일 끝에 덧붙이기 전에 기존 테스트를 먼저 읽는다. 같은 연동을 다른 샘플·설정으로 검증하는 시나리오는 `[Theory]`(`[InlineData]`/`[MemberData]`)로 **통합**하고, 서로 다른 흐름·실패를 뭉뚱그린 테스트는 시나리오별로 **분리**한다(→ `references/test-design.md`).
- 위 내용은 **`CLAUDE.md`의 지침을 항상 우선**한다. 충돌하면 `CLAUDE.md`를 따른다.

### 주석 — 무엇을, 어떤 연동을 검증하는지 명확히

테스트는 명세서다. 읽는 사람이 "이 시나리오가 어떤 컴포넌트 연동을, 왜 검증하는지" 즉시 알도록 간결·정확하게 주석을 단다.

- **테스트 메서드**: XML 문서 주석(`/// <summary>`)으로 어떤 흐름/경계를 검증하며 그것이 깨지면 무슨 문제가 나는지를 한국어로 적는다.
- **`[InlineData]`/`[MemberData]` 등 개별 케이스**: 그 케이스가 어떤 설정·입력·실패 상황을 대표하는지 한 줄 주석을 단다.
- 연동 결함을 박제하는 케이스라면 그 사실을 주석에 명시한다.
- **주석은 연동 동작을 말하고 내부 구현을 말하지 않는다**: 테스트 대상의 **내부 코드를 주석에 옮기지 않는다.** 내부 수치(임계값·매직넘버)나 특정 분기·알고리즘 단계를 직접 언급하지 말고, 관찰 가능한 흐름·경계 계약·결과로 적는다. 주석은 명세이므로 구현이 바뀌어도 살아남아야 하며, 내부에 묶인 주석은 리팩터링과 함께 썩는다.

작성 예시·패턴(Fixture, 임시 DB/디렉터리, 실패 재현, 시나리오별 주석)은 `references/conventions.md`와 `references/test-design.md`에 있다.

## 5. 검증과 마무리

- 작성한 통합 테스트 프로젝트를 **빌드하고 실행**해 컴파일·통과를 확인한다. (`dotnet test`; 빌드 전 `MSBUILD_EXE_PATH` 환경변수가 설정돼 있으면 해제한다.)
- **정리 검증**: 테스트가 만든 임시 DB·파일·디렉터리가 남지 않는지, 반복 실행해도 자원이 쌓이지 않는지 확인한다.
- 실패한 테스트가 연동 결함을 가리키면, 테스트를 약화시키지 말고 결함을 사용자에게 보고한다. 수정으로 이어질 수 있게 한다.
- 새 통합 테스트 프로젝트를 만들었으면 `.sln`에 `Tests` 솔루션 폴더(원본과 동일 구조)로 추가한다.
- 통합 테스트는 느릴 수 있으므로 `[Trait]`로 분류해 필요 시 따로 실행할 수 있게 한다(`dotnet test --filter "Category!=Integration"`로 단위만 빠르게).

## 6. 독립 검증 — 검증 에이전트 협상 루프

테스트가 컴파일·통과됐다고 의미 있는 연동 시나리오가 빠짐없이 망라됐다는 뜻은 아니다. 테스트를 만든 내가 스스로 채점하면 시나리오를 도출할 때의 맹점이 그대로 남는다. 그래서 **컨텍스트를 공유하지 않는 검증 에이전트**에게 연동 소스만 넘겨 필요한 시나리오를 독립적으로 재도출하게 하고, 그 결과와 내 테스트를 대조한다.

- 검증자는 **일반 서브에이전트**로 띄우고(**`fork` 금지** — 메인 컨텍스트 상속으로 독립성이 깨진다), **컴포넌트 소스·테스트 파일 경로만** 준다. 내 시나리오 도출 근거는 넘기지 않는다.
- 검증자가 반환한 판정(PASS/FAIL + 누락 gap 목록)은 **무조건 옳다고 가정하지 않는다.** 항목별로 정당한 지적은 시나리오를 추가하고, 잘못된 지적은 **코드 근거로 반박**하며, 같은 검증자 인스턴스(`SendMessage`)와 근거를 주고받아 타협점을 찾는다. 특히 **실제 자원을 Mock으로 대체해 연동 검증이 무의미해진 지적(over-mocked)** 은 진지하게 다룬다.
- 검증자가 `PASS`를 줄 때까지 반복하되, **횟수 상한(3~5회)** 과 **무진전 감지**로 교착 시 미해결 쟁점을 사용자에게 보고한다.

**절차·검증자 프롬프트·판정 형식·협상/종료 규칙은 반드시 `references/verification-loop.md` 를 읽고 그대로 따른다.**

## 7. 보고서 생성 (마지막 단계)

테스트 작성·검증이 끝나면 작업 내용을 정리한 **Markdown 보고서**를 만든다. 보고서는 사용자가 무엇을·어떤 연동을 왜 테스트했는지, 어떤 리팩터링과 개선점이 있었는지를 코드 없이도 이해하게 하는 산출물이다.

**형식·작성 규칙·예시는 반드시 `references/report-format.md` 를 읽고 그대로 따른다.** 핵심 요건만 요약:

- **구조는 실제 코드를 그대로 비춘다 — `Project → Class → Method`.** 헤딩 depth로 작성한 테스트 프로젝트(`##`) → 테스트 클래스(`###`) → 테스트 메서드(`####`) 트리를 만들고, **각 노드 이름은 실제 프로젝트명·클래스명·메서드명을 그대로** 쓴다(개념적 별칭으로 묶거나 한국어로 바꾸지 않는다). 독자가 목차를 보고 코드에서 같은 이름을 1:1로 찾을 수 있어야 한다.
- **맨 위는 링크된 목차**이며, 목차는 **Method 레벨까지** 펼친다(클래스 아래 각 메서드가 앵커 링크로 나열됨). 설명은 목차가 아니라 각 노드의 본문에 단다.
- **각 범위(Project/Class/Method)마다 설명 본문을 단다.**
  - **Project 수준**: 무엇과 무엇을 연동해 검증하는지, 공통 격리·정리 전략, 프로젝트 전반 리팩터링(이유·방향·동작보존), 개선 제안. 클래스마다 반복되는 공통 사항은 여기서 한 번에 설명한다.
  - **Class 수준**: 이 클래스가 묶어서 검증하는 연동 단위/경계 계약. 클래스 고유의 자원·격리·리팩터링이 있으면 함께. 없으면 한 줄만 두고 메서드로 내려간다.
  - **Method 수준**: 이 메서드가 어떤 연동/계약을 보장하며 깨지면 무슨 문제인지, 상황→관찰 가능한 기대 결과. `[InlineData]`가 여럿이면 케이스별 한 줄. 연동 결함을 박제한 메서드면 그 사실을 명시.
- 시나리오에 메서드가 여럿이어도 **묶지 말고 각 메서드를 `####`로 편다.** `[Theory]` 한 메서드 안의 여러 `[InlineData]` 케이스만 그 메서드 본문에서 표/목록으로 설명한다.
- 저장 위치/파일명은 `references/report-format.md`의 규칙을 따른다(기본 `<Project>.Report.md`, Windows 파일명 규칙 준수 — 콜론 금지).
