# Unit Test Creator

C#/.NET 코드에 대해 **동작(behavior)을 검증하는** 단위 테스트를 만든다. 단순히 통과하는 테스트가 아니라, 대상의 모든 실행 경로를 망라하고 구현의 결함까지 드러내는 테스트를 목표로 한다. 테스트가 불가능한 구조라면 먼저 테스트 가능한 구조로 리팩터링한다.

이 스킬의 가치는 **빠짐없는 케이스 설계**와 **저장소 관례에 정확히 맞는 산출물**에 있다. 아래 절차를 순서대로 따른다.

## 0. 입력 확인 — 대상이 무엇인가

테스트 대상은 **프로젝트 / 클래스 / 메서드 / 파일·폴더 경로** 중 하나로 주어진다.

- 대상이 명시되지 않았으면 **임의로 추측하지 말고** 사용자에게 무엇을 테스트할지 되묻는다.
- 프로젝트가 주어지면, 그 안의 테스트 가치가 높은 타입(공개 동작·복잡한 분기·핵심 로직)을 먼저 식별하고 사용자와 범위를 합의한다. 전부를 한 번에 하려 하지 말 것.
- 대상이 한 메서드여도, 그 메서드가 속한 클래스·의존성·호출 경로를 함께 본다.

**접근 제한자 규칙(중요):** 접근 제한자가 `internal` **이상**(internal/public)인 멤버만 테스트 대상으로 삼는다. `private`/`protected`를 테스트하려고 접근 제한자를 올리지 않는다. 동작은 항상 공개 표면(public/internal API)을 통해 검증한다. `internal`을 테스트하려면 접근 제한자 변경이 아니라 `InternalsVisibleTo`로 접근한다(→ `references/conventions.md`).

## 1. 대상 분석 — 구현과 사용처를 함께 본다

테스트 케이스는 분석의 질을 넘지 못한다. 다음을 파악한다.

- **구현**: 대상 메서드의 모든 `return` 지점, 모든 조건 분기(if/switch/삼항/널 병합/패턴 매칭/짧은 회로), 루프 경계, 던지는 예외, 부수 효과(상태 변경·이벤트 발생·의존성 호출).
- **계약**: 매개변수의 의미와 허용 범위, 널 허용 여부, 반환값의 의미, 던질 수 있는 예외.
- **의존성**: 생성자/메서드가 받는 타입, 그중 외부 자원(파일·DB·UI·네트워크)에 닿는 것. 이것들이 테스트 가능성과 모킹 전략을 좌우한다.
- **현재 사용처**: 호출하는 쪽이 실제로 어떤 입력을 넘기는지. 여기서 "현실적으로 발생 가능한 입력"과 "지금은 안 들어오지만 계약상 가능한 입력"을 구분해 케이스로 만든다.

분석 범위가 넓으면(여러 파일을 훑어야 하면) `Explore`/`general-purpose` 에이전트로 사용처·의존성을 조사하고, 결론만 가져와 정리한다.

## 2. 테스트 가능성 판단 — 안 되면 먼저 리팩터링

대상이 결정론적으로, 외부 자원 없이, 빠르게 테스트되는 구조인지 본다. 다음 신호가 있으면 **테스트 작성 전에 리팩터링을 제안**한다. 제안할 때는 항상 **(a) 왜 테스트가 막히는지 (b) 어떤 방향으로 바꿀지 (c) 동작이 보존되는지**를 함께 설명하고 사용자 동의를 받는다.

- **`ServiceLocator`/정적 컨테이너로 의존성을 끌어옴** → 생성자 주입으로 전환. (→ `references/refactoring.md`)
- **UI 의존성**(`MessageBox`, 다이얼로그, `Dispatcher`, UI에서만 동작하는 서비스 등) → 인터페이스로 추상화해 Mock 가능하게. **단, Mock을 위해 메서드를 `virtual`로 바꾸는 방식은 쓰지 않는다.** (→ `references/refactoring.md`)
- `new`로 직접 만든 구체 의존성(파일시스템·시간·랜덤·DB)이 동작을 좌우 → 인터페이스 주입.
- `static` 가변 상태에 의존 → 테스트 간 격리 불가, 주입 가능한 형태로.

리팩터링은 **동작을 바꾸지 않는 범위**에서 최소로 한다. 테스트화에 불필요한 구조 변경은 하지 않는다.

자세한 패턴·예시는 **`references/refactoring.md`** 를 읽고 적용한다.

## 3. 테스트 케이스 설계 — 모든 경우의 수

분석을 토대로, 아래를 **빠짐없이** 케이스로 만든다. 각 항목이 왜 필요한지·어떻게 빠짐없이 도출하는지는 **`references/test-design.md`** 에 정리돼 있다.

- 함수의 **모든 `return`** 경로
- 함수 내부의 **모든 조건 분기**(switch의 default·미정의 enum 포함)
- **정상 입력**과 **비정상 입력**(null, 빈 컬렉션, 잘못된 형식)
- 입력 값이 **극치**인 경우(0, 음수, 최대/최소, 경계값, 오버플로 직전, 매우 큰 컬렉션)
- **예외가 발생**하는 경우(어떤 예외·언제)
- **구현상 문제가 발생할 수 있는 경우**(off-by-one, 정수 나눗셈/오버플로, 부동소수 비교, 인코딩, 동시성, 자원 해제, 무한 루프)
- **현재 사용처에서 실제로 들어오는 입력**

> 동작을 검증하라 — 구현 방식이 아니라. 내부 호출 순서나 private 상태가 아니라, **관찰 가능한 결과**(반환값·던진 예외·공개 상태 변화·주입된 의존성에 대한 검증)를 단언한다. 케이스를 만들다 구현 결함(처리 안 된 분기, 잘못된 경계, 삼킨 예외)을 발견하면, 테스트로 박제하고 사용자에게 보고한다.

## 4. 테스트 작성 — 저장소 관례에 맞게

**작성 전에 반드시 `references/conventions.md` 를 읽는다.** 프로젝트 위치·명명·csproj 구성·라이브러리 버전·`InternalsVisibleTo`·폴더 구조가 모두 거기 정의돼 있다. 핵심만 요약:

- **프레임워크/라이브러리**: xUnit, 단언은 **AwesomeAssertions**(네임스페이스는 `using FluentAssertions;`), 모킹은 **NSubstitute**(필요할 때만 참조). Bogus/AutoFixture는 현재 저장소에서 쓰지 않으므로 기본은 인라인 데이터/팩토리 헬퍼이며, 정말 필요할 때만 패키지를 추가한다.
- **위치/구조**: `Tests/` 루트 아래 원본 폴더 구조를 미러링. 프로젝트명 `<대상프로젝트>.Tests`, 클래스 `<대상클래스>Tests`.
- **메서드명**: `Method_Scenario_ExpectedResult`. 예외 케이스는 결과를 `ThrowsXxx`로.
- **`internal` 대상**: 소스 csproj에 `<InternalsVisibleTo Include="...Tests" />` 추가(접근 제한자 변경 금지).
- **기존 테스트가 있으면 그 위에 정리한다**: 대상 클래스에 이미 테스트가 있으면 새 케이스를 끝에 덧붙이기 전에 기존 테스트를 먼저 읽는다. 같은 동작을 다른 입력으로 검증하는 케이스는 `[Theory]`로 **통합**하고, 서로 다른 상황을 뭉뚱그린 테스트는 관심사별로 **분리**한다. 흩어지거나 뭉친 테스트는 무엇이 커버되는지 읽기 어렵다(→ `references/test-design.md`).
- 위 내용은 **`CLAUDE.md`의 지침을 항상 우선**한다. 충돌하면 `CLAUDE.md`를 따른다.

### 주석 — 무엇을 테스트하는지 명확히

테스트는 명세서다. 읽는 사람이 "이 케이스가 무엇을, 왜 검증하는지" 즉시 알도록 간결·정확하게 주석을 단다.

- **테스트 메서드**: XML 문서 주석(`/// <summary>`)으로 검증 대상 동작과 그것이 깨지면 무슨 일이 나는지(중요성)를 한국어로 적는다.
- **`[InlineData]` 등 개별 케이스**: 해당 줄 끝/위에 그 케이스가 어떤 상황·입력을 대표하는지 한 줄 주석을 단다.
- 구현 결함을 박제하는 케이스라면 그 사실을 주석에 명시한다.
- **주석은 동작을 말하고 구현을 말하지 않는다**: 테스트 대상의 **내부 코드를 주석에 옮기지 않는다.** 내부 수치(임계값·매직넘버)나 특정 분기("switch의 default", "두 번째 if")를 직접 언급하지 말고, 관찰 가능한 상황과 기대 결과로 적는다. 주석은 명세이므로 구현이 바뀌어도 살아남아야 하며, 내부에 묶인 주석은 리팩터링과 함께 썩는다. (예: "임계값 0.05 초과" → "임계값 초과"; "default 분기 도달" → "정의되지 않은 종류는 기본 처리로 떨어진다".)

작성 예시·패턴(`CreateSut` 팩토리, stub 내부 클래스, NSubstitute 검증, 케이스별 주석)은 `references/conventions.md`와 `references/test-design.md`에 있다.

## 5. 검증과 마무리

- 작성한 테스트 프로젝트를 **빌드하고 실행**해 컴파일·통과를 확인한다. (`dotnet test`; 빌드 전 `MSBUILD_EXE_PATH` 환경변수가 설정돼 있으면 해제한다.)
- 실패한 테스트가 구현 결함을 가리키면, 테스트를 약화시키지 말고 결함을 사용자에게 보고한다. 수정으로 이어질 수 있게 한다.
- 새 테스트 프로젝트를 만들었으면 `.sln`에 `Tests` 솔루션 폴더(원본과 동일 구조)로 추가한다.
- **빠르게** 수행되는 테스트를 유지한다. 실제 파일·DB·네트워크·UI를 건드리는 테스트는 단위 테스트에 두지 않는다(필요하면 `.IntegrationTests`로 분리).

## 6. 독립 검증 — 검증 에이전트 협상 루프

테스트가 컴파일·통과됐다고 케이스가 빠짐없이 망라됐다는 뜻은 아니다. 테스트를 만든 내가 스스로 채점하면 케이스를 도출할 때의 맹점이 그대로 남는다. 그래서 **컨텍스트를 공유하지 않는 검증 에이전트**에게 소스만 넘겨 필요한 케이스를 독립적으로 재도출하게 하고, 그 결과와 내 테스트를 대조한다.

- 검증자는 **일반 서브에이전트**로 띄우고(**`fork` 금지** — 메인 컨텍스트 상속으로 독립성이 깨진다), **소스·테스트 파일 경로만** 준다. 내 케이스 도출 근거는 넘기지 않는다.
- 검증자가 반환한 판정(PASS/FAIL + 누락 gap 목록)은 **무조건 옳다고 가정하지 않는다.** 항목별로 정당한 지적은 테스트를 추가하고, 잘못된 지적은 **코드 근거로 반박**하며, 같은 검증자 인스턴스(`SendMessage`)와 근거를 주고받아 타협점을 찾는다.
- 검증자가 `PASS`를 줄 때까지 반복하되, **횟수 상한(3~5회)** 과 **무진전 감지**로 교착 시 미해결 쟁점을 사용자에게 보고한다.

**절차·검증자 프롬프트·판정 형식·협상/종료 규칙은 반드시 `references/verification-loop.md` 를 읽고 그대로 따른다.**

## 7. 보고서 생성 (마지막 단계)

테스트 작성·검증이 끝나면 작업 내용을 정리한 **Markdown 보고서**를 만든다. 보고서는 사용자가 무엇을 왜 테스트했는지, 어떤 리팩터링과 개선점이 있었는지를 코드 없이도 이해하게 하는 산출물이다.

**형식·작성 규칙·예시는 반드시 `references/report-format.md` 를 읽고 그대로 따른다.** 핵심 요건만 요약:

- **구조**: `Project → Class → Method`를 헤딩 depth로 나눈 트리. 맨 위에 **링크된 목차**로 시작한다.
- **Class 수준**: 클래스 단위 리팩터링이 있었으면 그 **이유와 작업 방향**을 쓰고, 추가로 개선하면 좋을 점이 있으면 함께 적는다. 둘 다 없으면 본문 없이 헤딩만 둔다.
- **Method 수준**: **테스트 목적**과 **각 테스트 케이스가 무엇을 검증하는지**를 사용자가 이해하도록 설명한다. 대상 함수를 리팩터링했으면 그 **이유와 방향**을, 대상 함수에 개선할 점이 있으면 그 점을 함께 설명한다.
- 저장 위치/파일명은 `references/report-format.md`의 규칙을 따른다(Windows 파일명 규칙 준수 — 콜론 금지).
