# 테스트 케이스 설계 — 모든 경우의 수 도출법

목표는 **빠짐없는 동작 검증**이다. "통과하는 테스트 몇 개"가 아니라, 대상의 모든 실행 경로와 계약 경계를 케이스로 박제해 구현 결함까지 드러낸다. 아래 체크리스트를 대상 메서드마다 적용한다.

## 1. 모든 `return` 경로

메서드의 각 `return` 문을 도달시키는 입력을 하나씩 만든다. early-return, 가드 절, 정상 종료를 모두 포함한다. 같은 값을 반환해도 **경로가 다르면 다른 케이스**다.

## 2. 모든 조건 분기

- `if/else if/else`: 각 분기를 참으로 만드는 입력 + 모두 거짓인 입력.
- `switch`: 각 `case` + **`default`**. enum이면 정의된 값 전부 + **미정의 값**(`(MyEnum)9999`)으로 default 분기 검증.
- 삼항·널 병합(`??`)·널 조건(`?.`): 양쪽 결과.
- 패턴 매칭: 각 패턴 + 미매칭.
- 짧은 회로(`&&`, `||`): 양변이 각각 평가를 결정하는 조합.
- **복합 조건**: `a && (b || c)` 같은 식은 각 부울 변수가 결과를 뒤집는 경계 조합을 만든다.

> 분기를 빠짐없이 셀 때 순환 복잡도를 떠올린다 — 독립 경로 수만큼의 케이스가 최소선이다.

## 3. 정상 입력과 비정상 입력

- **정상**: 대표적인 유효 입력 1~2개(동작이 다르면 더).
- **비정상**: `null`, 빈 문자열/공백, 빈 컬렉션, 잘못된 형식, 범위 밖 값, 잘못된 enum. 각각에 대해 "막아야 하는데 막는가 / 처리해야 하는데 처리하는가"를 본다.

## 4. 극치(경계) 입력

- 수치: `0`, 음수, `int.MaxValue`/`MinValue`, 경계 바로 안/밖(off-by-one 탐지), 오버플로 직전.
- 컬렉션: 0개, 1개, 매우 많은 개수, 중복 원소, 정렬 안 된 입력.
- 문자열: 빈 문자열, 매우 긴 문자열, 유니코드/멀티바이트, 개행·제어문자.
- 부동소수: `0.0`, 음수, `NaN`, `Infinity`, 정밀도 경계.

## 5. 예외 발생

계약상/구현상 예외를 던지는 입력을 만들고 **예외 타입**까지 단언한다. 어떤 입력이 어떤 예외를 언제 던지는지 명확히. 던지지 **않아야** 하는 경계(예: 빈 입력은 예외가 아니라 빈 결과)도 함께 검증한다.

## 6. 구현상 문제가 생길 수 있는 지점 (적극적 탐색)

분석 중 다음을 의심하고, 의심되면 그 경계를 찌르는 케이스를 만든다.

- **off-by-one**: 인덱스/길이/경계 비교(`<` vs `<=`).
- **정수 연산**: 0 나눗셈, 정수 나눗셈 절삭, 오버플로/언더플로.
- **부동소수 비교**: `==` 사용, 누적 오차.
- **널 처리 누락**: 중간 결과가 null일 수 있는 경로.
- **인코딩/문화권**: `ToString`/`Parse`가 `CultureInfo`에 의존(예: 소수점·천단위). 테스트는 `CultureInfo.InvariantCulture`를 명시.
- **자원 해제**: `IDisposable`이 누수 없이 해제되는지(필요 시 stub으로 호출 추적).
- **상태/순서 의존**: 같은 인스턴스에 두 번 호출, 멱등성, 재진입.
- **동시성**: 공유 상태가 있으면 경합 가능성(단위 테스트에서 다루기 어려우면 설계 문제로 보고).

## 7. 현재 사용처에서 실제로 들어오는 입력

분석 1단계에서 수집한 호출부의 실제 인자를 케이스로 만든다. "지금 실제로 발생하는 시나리오"와 "계약상 가능하지만 아직 안 들어오는 입력"을 구분해 둘 다 다룬다 — 전자는 회귀 방지, 후자는 미래 안전.

## 케이스를 코드로 옮기기

### `[Theory]` + `[InlineData]` — 같은 동작·다른 데이터

입력만 다르고 동작이 같은 케이스들은 `[Theory]`로 묶고, **각 줄에 그 케이스가 무엇을 대표하는지** 주석을 단다.

```csharp
/// <summary>
/// ReadBits(n): MSB부터 n비트를 정수로 읽는다. 비트 폭 경계가 깨지면
/// H.264 헤더 파싱이 전부 어긋나므로 핵심 경로다.
/// </summary>
[Theory]
[InlineData(0xB0, 4, 0b1011)]  // 상위 4비트만 — 부분 읽기
[InlineData(0xAB, 8, 0xAB)]    // 한 바이트 전체 — 경계 일치
[InlineData(0x00, 4, 0)]       // 전부 0 — 하한
[InlineData(0xFF, 8, 0xFF)]    // 전부 1 — 상한
public void ReadBits_GivenBitCount_ReturnsMsbFirstValue(byte data, int count, int expected)
{
    var reader = new BitReader([data]);

    reader.ReadBits(count).Should().Be(expected);
}
```

### `[Fact]` — 단일 시나리오

분기/시나리오가 고유하면 `[Fact]` 하나로 명확히. 메서드명과 `<summary>`로 무엇을 검증하는지 드러낸다.

```csharp
/// <summary>
/// 정의되지 않았거나 처리 대상이 아닌 타입은 모두 DefaultConverter(원본 통과)로 떨어진다.
/// 새 포맷을 빠뜨리면 조용히 원본 통과되므로, 미지정·범위 밖 입력이 안전하게 기본 처리됨을 박제한다.
/// </summary>
[Theory]
[InlineData(MediaStreamType.None)]       // 명시적 None
[InlineData(MediaStreamType.Undefined)]  // 미정의
[InlineData((MediaStreamType)9999)]      // enum 범위 밖 — 정의되지 않은 값
public void GetConverter_UnknownOrNoneType_ReturnsDefaultConverter(MediaStreamType type)
{
    VideoConverterFactory.GetConverter(type).Should().BeOfType<DefaultConverter>();
}
```

### 기존 테스트에 케이스를 더할 때 — 붙이지 말고 정리한다

대상 클래스에 테스트가 이미 있으면, 새 케이스를 파일 끝에 그냥 덧붙이지 말고 **기존 테스트를 먼저 읽고 전체를 하나의 응집된 스위트로 다듬는다.** 판단 기준은 언제나 **"관찰 동작이 같은가"** 다.

- **통합**: 새 케이스가 기존 `[Fact]`와 같은 동작을 다른 입력으로 검증하면, 그 `[Fact]`를 `[Theory]`+`[InlineData]`로 바꿔 한곳에 모은다. 같은 것을 검증하는 테스트가 흩어져 있으면 커버리지를 읽기 어렵고 중복이 쌓인다.
- **분리**: 한 테스트가 서로 다른 상황·기대 결과를 뭉뚱그려 단언하고 있으면 관심사별로 쪼갠다. 실패했을 때 이름만 보고 무엇이 깨졌는지 알 수 있어야 한다.
- 통합·분리로 손댄 기존 테스트도 반드시 다시 통과시킨다.

### 구현 결함을 발견하면

케이스를 만들다 "이건 버그다" 싶은 동작(처리 안 된 분기, 잘못된 경계, 삼켜진 예외, 잘못된 결과)을 찾으면:

1. 그 동작을 드러내는 테스트를 작성한다.
2. **테스트를 현재의 잘못된 동작에 맞춰 통과시키지 않는다.** 올바른 기대값으로 작성해 실패하게 두고,
3. 사용자에게 "이러이러한 입력에서 이런 결함이 보인다, 기대 동작은 이렇다"고 보고해 **수정으로 이어지게** 한다. 사용자가 수정을 원하면 구현을 고치고 테스트를 통과시킨다.

이 스킬의 목적은 통과하는 테스트가 아니라 **올바른 동작의 박제**다.

## 동작 검증 vs 구현 검증

| 검증할 것(O) | 피할 것(X) |
|---|---|
| 반환값 | private 필드 값 직접 확인 |
| 던진 예외(타입) | 내부 메서드 호출 순서 자체 |
| 공개 상태 변화 | 구현 세부에 묶인 호출 횟수(의미 없는) |
| 주입된 의존성에 대한 의미 있는 상호작용(`Received`) | 리팩터링하면 깨지는 구조 의존 |

의존성 검증(`Received`)은 그 호출이 **관찰 가능한 계약**일 때만 한다(예: "삭제를 확정하면 리포지토리의 Delete가 호출된다"). 단순히 "내부적으로 A를 부른다"는 구현 검증이므로 피한다.

**예외는 타입만 단언한다.** 어떤 예외가 나는지는 계약이지만, 고정된 문자열 메시지는 구현 세부이고 쉽게 바뀐다 — 메시지에 의존하면 문구만 손봐도 테스트가 깨진다. `act.Should().Throw<ArgumentNullException>()`까지가 검증이고, `.WithMessage("...")`로 고정 메시지를 확인하는 것은 구현 검증이므로 하지 않는다(메시지가 그 자체로 계약인 특수한 경우가 아니라면).
